## UART 컨트롤러
Verilog와 테스트벤치 환경에 익숙해 지기 위한 첫번째 프로젝트는 UART 컨트롤러 제작이다.
향후 구현할 하드웨어는 모두 Verilog로 구현되기 때문에 Verilog와 테스트벤치 작성 방법과
MMIO의 개념, 그리고 세미호스팅(semihosting)을 사용하여 디버깅하는 방법을 익혀야 한다.

### Verilog 기본 개념들
Verilog는 지금까지 사용해왔던 프로그래밍 언어와 굉장히 다른 언어였다.

필수로 익혀야 하는 개념들:
- wire와 reg의 하드웨어적 동작
- 블록킹과 논블록킹 
- 유한 상태 머신
- 테스트 벤치 작성
- 타이밍 다이어그램 분석

### 패킷 처리
UART 패킷을 구성하는 것은 어렵지 않았다. 

![uart packet 구조]()

단순화를 위해 단방향으로만 통신하기 때문에 TX 혹은 RX 신호에 따라 전송자 혹은 수신자가 활성화 된다.
한쪽에서 데이터를 보내면 다른 한쪽은 데이터를 받는다.

오히려 가장 헷갈렸던 부분은 대기상태일 때는 어떤 신호를 처리해야 하는지 였다.

UART 패킷의 형태와 구성 모듈에 관한 자료는 많았는데 전체 과정을 이해하기 쉽게 작성된 자료는 찾기 어려웠다.

> 그러던 중, [이곳]()에서 힌트를 얻을 수 있었다.
> 
> 아마 실제 하드웨어가 있고 오실로스코프와 같은 측정기기를 사용할 수 있었다면 좀 더 쉬웠을 것 같다.
> 나중에 설명할 CPU 구현 역시 실제로 동작하는 하드웨어를 사용해서 비교를 할 수 있다면 더 완성도가 높아질 것 이다.

### Verilator로 전환
Verilog로 작성된 모듈은 파이썬 시뮬레이터 프레임워크를 사용하고 있다.
하지만, 나중에 진행될 네트워크 스택개발 등 호스트 PC와의 긴밀한 연계가 필요한 기능을 고려했을 때, C++기반의 Verilator로 전환하는 것이 유리해보인다.

## 32비트 ARM CPU
UART 컨트롤러 구현 이후에는 갑자기 훨씬 더 복잡한 32비트 ARM CPU 제작을 해야했다.

가장 먼저 ARM CPU의 구성과 동작방식을 파악하기 위해 [ARM7TDMI 공식문서]()를 참고했다.

> 구현 작업 중에 가장 중요하고 도움이 되었던 것은 타이밍 다이어그램 생성과 분석이었다.
> 처음에는 테스트벤치 로그로만 디버깅을 했는데, 문제 해결을 위한 고민보다 로그 출력에 관한 고민을 더 많이해야 해서 그만뒀다.
> 테스트 벤치로 생성 가능한 타이밍다이어그램 파일을 실시간으로 리로드하면서 코드 변경에 따른 신호 타이밍을 추적할 수 있어서 훨씬 효율적이다.
>
> ![이미지]()

- 산술 논리 장치
- 명령어 디코더

각 모듈은 결국 CPU가 명령어를 다루는 방법

### 논파이프라인 구조 채택
실제 ARM CPU는 명령어 파이프라인 구조를 사용하고 있다.

![파이프라인 구조]()

파이프라인 구조는 현대의 대부분의 CPU에서 사용하고 있을만큼 중요하지만 지금 단계에서는 구현하지 않기로 결정했다.
단지 효율성과 성능이 하락할 뿐 CPU의 동작 자체에는 영향을 주지 않기 때문에 프로젝트 1차 완료를 목표로 한 시점에서는 오버스펙이었기 때문이다.

![논파이프라인 구조]()

각 상태전이는 유한 상태 머신을 사용하고 최대한 적은 사이클에서 하나의 명령어를 수행할 수 있도록 노력했다.

## 부트롬
CPU에서 실행하는 이진코드를 매번 하드코딩할 수 는 없고 실제 CPU도 그렇게 동작하지 않는다.
CPU는 메모리(RAM이던 ROM이던)로부터 명령어를 읽어야 한다.
우리가 만들어야 하는 것은 소프트웨어로 구현된 완전한 컴퓨터이기 때문에, 기존의 컴퓨터와 동일하게 부트롬 코드를 가장 먼저 실행해야 한다.

부트롬과 부트로더는 무엇이고 어떤 차이점이 있는지를 이해하기 위해선 컴퓨터가 부팅되는 과정을 알아야 한다.

### 컴퓨터의 부팅 과정
일반적으로 x86기반의 컴퓨터에서 실행되는 응용소프트웨어 개발분야는 프로그램이 실행되는 컴퓨터의 부팅과정을 이해할 필요가 없다.
어차피 이미 부팅된 컴퓨터에서 실행되고 소프트웨어의 동작이 부팅과정의 영향을 받지 않기 때문이다.

![컴퓨터 부팅]

### 메모리 맵 설계
이제 부트롬과 부트로더가 필요하다는 것을 알았다. 그럼 부트롬 코드는 어디에서 어떻게 실행해야 할까?라는 문제가 생긴다.
보통 부트롬 코드는 변하지 않는다. 변하지 않는 다는 것은 컴퓨터가 언제 어떻게 실행되어도 동일한 부트롬 코드를 실행해야 한다는 의미이다.
그렇기 때문에 RAM과 같은 휘발성 메모리가 아니라 ROM이나 플래시 메모리에 적재되어 읽기 전용으로 실행되야 한다.

하지만, 앞으로 개발할 다른 소프트웨어들 역시 CPU가 실행할 수 있는 명령어(이진코드)로 이루어져 있고, 
이런 이진코드들은 다양한 상황에 의해서 유동적으로 변할 수 있다.

그렇기 때문에 CPU 입장에서는 본인이 실행할 명령어가 어디에 있는지 알 수 있어야 한다.

### CPU와 메모리 버스 연결

## ARM 어셈블러
이제 조금 더 상위의 추상화 레벨로 이동한다. 지금까지 프로그램을 실행할 하드웨어의 기반을 만들었다면
프로그램의 동작을 기술하는 명령어 이진코드를 생성하기 위한 소프트웨어 기반이 필요하다. - 어셈블러다!

어셈블러 개발의 초점은 "내가 정말 제대로 이진코드를 생성한 것인가?"에 대한 확인이었다.
어셈블러는 어셈블리 코드를 읽고 타겟 하드웨어에 맞는 이진코드를 생성하는 것이 전부다.
ARM의 경우 [ARM architecture manual]()에서 상세하게 기술하고 있다.

대부분 시중의 도서나 온라인 자료에서는 실제 동작하는 ARM ISA가 아니라 단순화 시킨 커스텀 ISA를 사용하는 방식이었다.
이런 구현을 따를 경우 문제점은 

이런 이유로 참고할 수 있는 ISA 문서중 가장 오래되고, 그렇기에 단순한 ARMv4 기반의 ISA를 구현했다.

### 초기 구조
첫번째 버전에서는 레이블과 주소를 고려하지 않고 각 줄을 순차적으로 읽어서 토큰에 따라 파싱하고 ARMv4 ISA에 해당하는 이진코드를 생성하는 방식이었다.
32비트 구조이므로 각 명령어 한줄마다 32비트의 이진코드를 ISA포맷에 맞춰 생성한다.
하지만 이 경우, 명령어 주소를 사용하는 브랜치 명령(`b`)을 구현할 때 문제가 발생했다.

> 지금까지는 한개의 워드만큼 증가하는 주소를 별도로 저장할 필요가 없었다!

레이블 기반의 주소로 분기하기 위해선 각 레이블의 주소를 테이블 형태로 저장할 필요가 있었다.
레이블명-주소 쌍의 테이블이 있으면 브랜치 명령을 파싱할 때 해당 테이블을 참조하여 이동할 주소값을 이진코드로 변환할 수 있기 때문이다.

### 2-패스 파싱
현재는 파일을 2번 읽도록 구현했다.

1. 첫번째 패스
- 전처리(주석, 불필요 공백제거)
- 레이블 정보 저장
2. 두번째 패스
- 각 라인별 명령어를 이진코드로 변환

## C 컴파일러
다시 조금 더 상위의 소프트웨어 레벨로 이동한다.
ARM 어셈블러를 사용해서 우리가 작성한 어셈블리 코드를 이진코드로 변환할 수 있었다.
하지만, 현대의 컴퓨터 프로그래밍에서 어셈블리 코드만으로 프로그램을 작성하는 것은 쉽지않다.

### 컴파일러 배경지식
이론적인 부분은 크래프팅 인터프리터와 드래곤북을, 실제 구현은 Clang을 참고했다.
학부 전공과정에서 컴파일러 이론을 배우긴 했지만 워낙 오래되기도 했고 

### 크래프팅 인터프리터의 문제점
컴파일러 입문용으로 많이 추천하던 크래프팅 인터프리터는 초반 몇개의 장을 읽어본 것이 전부다.
드래곤북에 비해서 전반적인 내용을 실습위주로 쉽게 설명한 것이 장점이었다.

### 드래곤북의 문제점
많은 프로그래머가 드래곤북보다 크래프팅 인터프리터를 먼저 추천하지만,
나는 오히려 전통적인 컴파일러 이론서인 드래곤북이 크래프팅 인터프리터 보다 괜찮았다.

다만, 많은 내용들을 포함하고 있어서 필요한 내용들을 선별하는 것이 어려웠다. 
(이건 실제 컴파일러 코드와 chatgpt로 해결했다.)

### Clang 코드 분석
위 두개의 이론서 만으로는 실제 동작하는 컴파일러를 구현하는게 굉장히 막막했다.
또한 이전의 ARM 어셈블러 구현에서 직면한 문제와 비슷한 문제가 있었다.

***"내가 작성한 컴파일러가 제대로 동작하는 것이 맞는가?"***

결국 2개의 문제를 해결하기 위해 clang 코드를 세세하게 분석하고 동작해보는 과정이 필요했다.

당장의 다음에 추가할 기능은 컴파일러의 어셈블리 코드 생성 기능이다.
C코드가 어떤 어셈블리 코드를 생성하는지, 그리고 전반적인 어셈블리 코드의 동작을 익히기 위해 [어셈블리 튜토리얼]() 을 진행했었다.
어셈블리를 완전히 파악하는 것이 지금의 목표가 아니기 때문에 기본적인 튜토리얼만 완성하고 다시 컴파일러 작업을 할 것 같다.

```
컴파일러 -> 링커 -> C 라이브러리
```
이렇게 완전한 32비트용 ELF파일 생성까지 완료한 이후에는 지금까지 구현한 것들을 재정비해야 할 필요성을 느낀다.
각 모듈을 구조적/기능적인 리팩토링하고 오류처리를 추가하면서 문서화를 해야한다.
또한, ELF파일을 완전히 사용하기 위해서 기존에 Verilog로 작성한 하드웨어 모듈들을 연결해야 한다.
